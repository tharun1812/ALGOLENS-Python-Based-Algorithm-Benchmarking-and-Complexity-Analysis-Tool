# AlgoLens: measure algorithms, then infer their complexity from the data

Textbooks *tell* you that bubble sort is O(n²). AlgoLens **measures** it. It runs 11 sorting and 5 searching algorithms on
inputs of growing size, counts every comparison and array write, fits growth curves to the counts, and **infers each
algorithm's complexity class statistically**. It then checks the inferred class against textbook theory.

The interesting results come from changing the *input*: the same algorithm can be O(n), O(n log n) or O(n²) depending on
what you feed it, and AlgoLens shows exactly where and why.

## What it found

All **34 of 34** cases that have a textbook answer were recovered correctly from measurements alone. The tables below are
generated by `python -m algolens analyze sort` and `analyze search` (the CSVs are in `results/`).

### Sorting (inferred class of the comparison count)

| Algorithm | random | sorted | reversed | nearly sorted | few unique |
|---|---|---|---|---|---|
| bubble | O(n²) | O(n) | O(n²) | O(n²) | O(n²) |
| insertion | O(n²) | O(n) | O(n²) | O(n²) | O(n²) |
| selection | O(n²) | O(n²) | O(n²) | O(n²) | O(n²) |
| quick_naive | O(n log n) | O(n²) | O(n²) | O(n log n) | O(n²) |
| shell | O(n log n) | O(n log n) | O(n log n) | O(n log n) | O(n log n) |
| merge | O(n log n) | O(n log n) | O(n log n) | O(n log n) | O(n log n) |
| quick_median3 | O(n log n) | O(n log n) | O(n log n) | O(n log n) | O(n log n) |
| heap | O(n log n) | O(n log n) | O(n log n) | O(n log n) | O(n log n) |
| timsort | O(n log n) | O(n) | O(n) | O(n) | O(n) |
| counting | O(n)* | O(n)* | O(n)* | O(n)* | O(n)* |
| radix | O(n log n)* | O(n log n)* | O(n log n)* | O(n log n)* | O(n)* |

`*` = judged by array writes, because counting and radix sort make no comparisons at all.

What stands out:

- **Insertion and bubble sort** are O(n²) on random data but **O(n) on sorted data**: the empirical exponent is 1.01.
- **Naive quicksort** (first element as pivot) is O(n log n) on random data but collapses to **O(n²) on sorted, reversed
  and few-distinct-value input**. Median-of-three with Hoare partitioning stays O(n log n) on everything.
- **Selection sort** is O(n²) *even on sorted input*: it always does n(n-1)/2 comparisons, whatever the data.
- **Timsort** (Python's built-in) is O(n log n) on random input but **O(n)** on sorted, reversed, nearly sorted and
  few-distinct-value input, because it exploits existing runs. On random input it matches merge sort.
- **Radix sort** costs O(n·d) writes, where d is the number of digits. Keys that grow with n give O(n log n); keys limited
  to 8 distinct values need one pass, so O(n). An early version of this project's theory table got that wrong, and the
  measurement corrected it.

### Searching (average comparisons per query)

| Algorithm | Inferred class | Empirical exponent | Textbook | Comparisons per query at n = 131,072 |
|---|---|---|---|---|
| linear | O(n) | 1.001 | O(n) | 12034.7 (at n = 16,384) |
| binary | O(log n) | 0.11 | O(log n) | 18.0 |
| exponential | O(log n) | 0.123 | O(log n) | 32.1 |
| jump | O(sqrt n) | 0.491 | O(sqrt n) | 538.5 |
| interpolation | O(log log n) | 0.05 | O(log log n) | 16.7 |

Interpolation search grows like log log n, yet at n = 131,072 it makes 16.7 comparisons against binary search's 18.0.
Its asymptotic advantage is real but small until the data gets very large, and it only holds for evenly spread values.

## How the complexity is inferred

If an algorithm's cost really is c·f(n), then log(cost / f(n)) is the same constant at every size n. For each candidate
f (1, log n, n, n log n, n^1.5, n², n³ for sorting; 1, log log n, log n, √n, n for searching), AlgoLens computes how much
log(cost / f(n)) varies across the measured sizes (its standard deviation) and picks the candidate with the smallest
variation. When several fit about equally well, the **slowest-growing wins** (Occam's razor). It also reports the
**empirical exponent**, the slope of log cost against log n.

Two things worth knowing when reading the exponents:

- n log n is not a pure power law, so over these sizes it shows an exponent of about 1.1 to 1.3, not exactly 1.
- Costs are averaged over several random trials per size; sorted and reversed inputs are deterministic, so one trial.

## Quick start

```bash
python -m venv .venv && source .venv/bin/activate       # Windows: .venv\Scripts\activate
pip install -e .

algolens list                                  # algorithms and input types
algolens verify                                # every algorithm checked against Python's own sort and bisect
algolens analyze sort --quick                  # seconds: sizes up to 1,024
algolens analyze sort                          # the full experiment (about 15 seconds on a laptop)
algolens analyze search
algolens animate quick_median3 --out quick.gif
```

`analyze` writes measurements (CSV), the classification (CSV, JSON, Markdown report) and the charts into `results/`.
Useful flags: `--algorithms bubble merge`, `--inputs random sorted`, `--seed 7`, `--verbose`.

## How the counting works

Algorithms are written as ordinary, readable Python. The counting happens inside the objects they operate on:

- `Item` wraps an integer and increments a counter on every `<`, `<=`, `>`, `>=` and `==`.
- `TrackedList` is a list that counts every write (a swap is two writes) and can notify a callback, which is how the
  animations are recorded.

So an algorithm cannot forget to count, and Python's own `sorted()` can be measured too. Only writes to the main array are
counted; reading is free, and so is copying a slice into a temporary buffer.

## Testing

```bash
pip install -e ".[dev]"
python -m pytest -q                         # 462 test cases, about 15 seconds
HYPOTHESIS_PROFILE=deep python -m pytest    # property tests with 2,000 generated cases each
```

- Every sort is run on every input type and on edge cases (empty, one element, all equal, negatives), with
  property-based tests that the output is the sorted permutation of the input.
- Stable sorts are checked for stability.
- Instrumentation is validated against **exact counts that can be derived by hand**: bubble and insertion sort on sorted
  input make exactly n-1 comparisons, selection sort always makes exactly n(n-1)/2, naive quicksort on sorted input makes
  exactly n(n-1)/2, and so on.
- The classifier is tested on synthetic curves (exact and with 5% noise), for scale invariance and for the tie-breaking rule.
- A deliberately broken sort and a deliberately wrong search are injected to prove the experiments catch wrong answers
  instead of silently measuring them.

## Limitations

- Counts are the cost model, not wall-clock time. Real running time also depends on caches, memory layout and the language.
- The inferred class is the best fit within a fixed list of candidate models over sizes from 64 to 1,024 (quadratic sorts) or
  to 8,192 (the rest). It is evidence about growth in that range, not a proof of asymptotic behaviour.
- Shell sort's textbook complexity depends on its gap sequence and has no simple closed form, so no textbook value is
  claimed for it; the best fit is n log n with an exponent near 1.2.
- Radix sort requires non-negative integers and raises an error otherwise.
- The algorithms are pure Python on purpose (so every operation is countable) and are not tuned for speed.

## Adding an algorithm

Write `def my_sort(a: TrackedList) -> None` using ordinary comparisons and indexing, add a `SortSpec` to `SORTS` in
`sorting.py`, and (optionally) add its textbook class to `theory.py`. It is then verified, measured, classified and
charted automatically.
